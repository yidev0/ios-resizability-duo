# Evaluate and implement the adaptive baseline

Use this checklist in both modes. Evaluation produces findings, never source edits. Implementation completes each necessary migration, including callers and configuration. Adapt patterns to deployment support; check symbol availability before choosing an API.

## Project configuration

Inspect all app targets/configurations in scope, their plists, generated Info.plist settings, xcconfigs, and scene entry points. Keep app extensions distinct. Resolve conditional/inherited build settings before reporting an effective value.

- **Launch screen:** An iOS 27 SDK-or-later upload needs one of `UILaunchStoryboardName`, `UILaunchStoryboards`, `UILaunchScreen`, or `UILaunchScreens` in the built Info.plist. Missing all causes `ITMS-90870`. `INFOPLIST_KEY_UILaunchScreen_Generation` is a build input, not itself the final launch-screen key. Preserve a valid existing launch screen. [TN3208](https://developer.apple.com/documentation/technotes/tn3208-preparing-your-apps-launch-screen-to-meet-app-store-requirements)
- **Scene lifecycle:** Apple's June 2026 UIKit guidance makes scene lifecycle a launch requirement on iOS 27 for apps built with the new SDK. Treat a legacy app entry point as a prerequisite migration, not optional multi-window polish. Verify the exact SDK/runtime requirement when applying this dated guidance. [UIKit updates](https://developer.apple.com/documentation/updates/uikit)
- **Orientations:** For an iPad target, inspect `UISupportedInterfaceOrientations~ipad` (falling back to the unsuffixed declaration), plus controller overrides. Check all four orientations; missing declarations require resolving defaults rather than inventing a restriction. A portrait-only ordinary iPhone declaration is not automatically a bug. Evaluate its actual effect on Duo separately from orientation-as-layout mistakes.
- **Full-screen compatibility:** Record the Boolean value of `UIRequiresFullScreen`, not merely key presence, and `UIRequiresFullScreenIgnoredStartingWithVersion`. For an SDK 27+ build, `YES` normally selects **discrete resizing**; it cannot prevent resizing. An ignored-starting version of 27 or earlier disables that compatibility behavior on 27. Do not summarize the key as simply ignored by iOS 27. On Duo, folds still resize the scene. [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key)

Configuration edits belong to implementation after understanding the target behavior. Do not blindly remove a full-screen key at discovery: that can change older-OS behavior before layouts are ready. Build the layout fixes first; test the proposed opt-in in a simulator/test configuration before retaining it. Preserve an older-OS compatibility path where needed. If choosing a cutoff changes supported behavior beyond the request, present the concrete proposed value and its impact for a decision. Record unverified behavior honestly.

## Code audit by intent

Use `rg` within the authorized source tree. Search Swift, Objective-C/Objective-C++, storyboards, xibs, plists, xcconfigs, and project files as relevant. Exclude generated/vendor code from edits unless in scope, but report a dependency that prevents readiness. Initial search terms include `UIScreen.main`, `mainScreen`, `interfaceOrientation`, `UI_USER_INTERFACE_IDIOM`, `userInterfaceIdiom`, `connectedScenes`, `safeAreaInsets`, `topLayoutGuide`, `bottomLayoutGuide`, `UIRequiresFullScreen`, fixed `frame` values, `ignoresSafeArea`, and custom bars. Follow helpers and cached derivatives; a regex cannot establish completeness.

| Area | Inspect and fix |
| --- | --- |
| Screen/geometry | Replace global screen dimensions used for layout with the consuming view/container's bounds. Read display scale from local traits/environment. If a physical screen is truly required, obtain it dynamically from the relevant window scene. Pass context into helpers; never choose an arbitrary global scene/window. |
| Orientation | Use size classes for layout variants and local dimensions for sizing. Preserve genuine camera/rotation/directional semantics: width greater than height cannot distinguish left from right. On supported SDKs migrate scene geometry callbacks atomically, using current effective geometry and previous values. Keep older-runtime fallbacks. |
| Trait-derived values | Inline fresh values differ from cached images, layer scale, constraint constants, and one-time setup. Pair cached value changes with observation/recomputation and initial setup at the correct lifecycle phase. Use automatic tracking only in methods/OS versions documented to support it; otherwise register the specific traits or retain the older callback. |
| Scene lifecycle | UIKit window and per-scene UI responsibilities move to scene lifecycle; process-wide services stay with the app. Create windows with their scene, preserve storyboard/programmatic entry, and wire the manifest/delegate together. SwiftUI App/Scene apps already have scene lifecycle: do not add a redundant SceneDelegate. |
| Safe area/margins | Read the consuming view's current insets at layout time, each edge independently. Prefer guides for constraints; physical UIKit left/right is not directional leading/trailing. Preserve full-bleed artwork; inset interactive/readable foreground. Account for additional custom chrome once. Safe-area APIs are correct tools, not APIs to eliminate. |
| Scrolling/keyboard | Avoid adding safe area twice to `adjustedContentInset`. Keep justified custom scroll behavior; use automatic adjustment where appropriate. Prefer `keyboardLayoutGuide` when deployment permits; otherwise convert notification coordinates correctly and update on resize. Reserve actual bar space, not overlay padding guesses. |
| Idiom | Replace phone/tablet checks only when their intent is available layout space. Legitimate platform capabilities, analytics, asset selection, and behavior checks aren't automatically wrong; use local traits for a genuine UI idiom need. Read SwiftUI size classes from environment and handle nil. |
| SwiftUI | Check fixed sizes, layout priority, proposed-size handling, conditional root hierarchies, `.id` resets, geometry caches, and state ownership. Keep navigation path, selection, scroll position, editing draft, focus, and tasks continuous across resize. Use a stable container/model owner instead of recreating the entire app for compact/regular branches. |
| Custom controls/containers | Identify bespoke tab selectors, toolbars, navigation chrome, palettes, overlays and presentations by role—even without system bar types. Trace ownership/actions/state and identify missing Duo adaptation, then recommend system integration or explicit custom implementation. Use [custom-navigation.md](custom-navigation.md); title/Back controls are only examples. |

State migration includes URL/user-activity handling, notification entry, restoration, background/foreground transitions, and session reconnection. In evaluation list each route. In full implementation preserve and wire applicable routes; do not declare completion with migration TODOs that lose existing app behavior. App-level work must not run once per scene by accident. Supporting scene lifecycle does not require enabling multiple simultaneous instances unless the product needs it.

**Folding is not scene restoration.** Treat a normal outer/inner transition as an in-place geometry/trait change of the existing scene, not a reason to recreate controllers, restart playback, repeat a transaction, or reload the app. Test existing scroll and editing continuity before adding manual scroll restoration merely for a fold. Separately preserve real disconnect/reconnect and relaunch behavior through the app's restoration mechanism; UIKit's scene route uses `stateRestorationActivity(for:)` and `NSUserActivity`. [Official lab summary](https://developer.apple.com/forums/thread/847644), [restoration sample](https://developer.apple.com/documentation/uikit/restoring-your-app-s-state).

Audit `UserDefaults`, `@AppStorage`, and singleton-held selection, navigation paths, drafts, and presentation state. Defaults storage is shared within its configured store, not automatically isolated per window. Keep independent window state in a scene-owned model or explicitly identified per-scene persistence; retain genuinely shared preferences and document data. Do not confuse preserving a scene through folding with sharing all UI state between simultaneous scenes.

Trace forced size-class overrides, including `.environment(\.horizontalSizeClass, ...)`, UIKit trait overrides, and custom container propagation. A forced value can hide real transitions from descendants or system containers. Remove unjustified overrides; narrowly scoped compatibility overrides need a documented reason and tests. In hybrid apps, check `UIHostingController`, representables, containment, constraints, and trait/geometry updates on both sides of the boundary. Automatic trait tracking still depends on the actual method and OS version.

Preserve unrelated guards, nil handling, branching, and public contracts. A non-view helper may need an explicit context parameter and updated callers; check cross-module consumers before changing exported signatures. Do not substitute global `UITraitCollection.current` or deprecated forwarding just to force a diff. Correct candidates and genuine idiom/orientation uses can remain with a documented rationale.

For safe-area details, distinguish actual geometry from safe content geometry: don't subtract insets from an already-inset SwiftUI proposal. `GeometryReader` itself is not a defect. Read geometry only where necessary; use safe-area layout modifiers for ordinary inset placement. A custom reserved-region layout may legitimately use `GeometryProxy` on a supporting SDK.

## Completion discipline

Maintain one ledger for discovered sites and dependencies. Finish small coherent batches rather than doing all analysis and losing the tail of implementation. Record intentionally retained/dead/generated sites with reasons. Rescan after edits and inspect diffs for new global lookups, stale caches, unintended branch removal, and missing observers. A file with correct code needs no diff.

The baseline checklist adapts the user's supplied `xcode-skills/app-resizability/SKILL.md` and its `uiscreen-task.md`, `orientation-task.md`, `scene-lifecycle-task.md`, `safe-area-task.md`, and `idiom-task.md` references. Consult an installed copy when present; don't assume a particular user's home path on another machine.
